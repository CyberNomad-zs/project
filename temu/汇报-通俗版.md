# Temu 店铺自动监测 · 工作汇报（通俗版）

**汇报对象**：运营同事 / 业务领导  
**日期**：2026-08-06  
**当前版本**：Chrome 插件 **v19.3**（装好后图标点开应显示：`后台：v19.3-mallId绑店`）  
**一句话**：系统帮我们 24 小时盯多店「有没有掉链接 / 有没有被限流」，异常自动推飞书，减少人肉刷后台。

---

## 一、我们到底在解决什么问题？

半托管多个 Temu 店（如 Agnis、HomeCove、Twilight Cove），人工很难做到：

1. **及时发现下架 / 在售变少**——掉了链接才知道，损失已经发生  
2. **及时发现流量异常（限流）**——尤其自有款、热销款被限流要优先处理  
3. **多店切换来回看**——费时，还容易漏  

**目标**：异常自动进飞书群 → 运营按优先级处理；系统尽量 **少误报、少刷屏**。

---

## 二、现在怎么跑？（给领导的架构一句话）

我们用 **两条腿走路**，不把鸡蛋放一个篮子里：

| 谁在跑 | 装在哪 | 主要干什么 | 特点 |
|--------|--------|------------|------|
| **浏览器插件** | 同事日常 Chrome | ① 限流监测（分严重/一般）② 上下架实时兜底 ③ 每天两次状态汇报 | 快、准（直接看 Temu 后台）；**电脑要开着 Chrome，并留着商品列表页** |
| **公司服务器（赛狐）** | 固定云服务器 | 上下架备份监测 | **24 小时不关机**；有时会比后台慢一点 |
| ~~本机自动浏览器脚本~~ | — | 已不做日常 | 以前试过，登录麻烦、容易和日常浏览器冲突，已停发同事 |

```
同事电脑（插件）──快──► 飞书群
公司服务器（赛狐）──稳──► 飞书群
         业务判断以 Temu 卖家后台为准
```

## 三、飞书会推什么？运营怎么看？

### 1. 限流相关（只靠插件）

| 等级 | 含义（通俗） | 建议 |
|------|--------------|------|
| 🔴 **严重限流** | 货号 VIP 开头（自有），或 JM 开头且是热销款 | 优先处理 |
| 🟠 **一般限流** | 有限流，但不是上面两类 | 按排期处理 |
| ❌ 不推 | 已经下架的商品就算还有限流标记 | 不用管 |

**规则补充（减少吵闹）：**

- 同一商品 **6 小时内**一般不重复推  
- **切换店铺**时，不会把该店「原来就有的限流」再推一遍  
- 只有 **真正新出现** 的限流，才即时推  

### 2. 上下架相关（插件 + 服务器 两条都可能推）

| 类型 | 说明 |
|------|------|
| 在售数量变化 | 例如 15 变成 14；会先「确认一下」再推，避免页面加载中的假数字 |
| 下架点名 | 告诉你 **哪个商品** 没了，尽量带后台编辑链接 |
| 上架点名 | 新上的会 **连续确认两次** 再报，避免抖一下就报 |

**重要约定（已和研发对齐）：**

- 插件卡片会带 **「插件·后台」** 字样 → 表示来自 Temu 后台、较新  
- 赛狐卡片 **没有** 这几个字 → 来自服务器备份通道  
- **同一商品偶尔会收到两张卡**（插件一张 + 赛狐一张）——这是故意的「双保险」，**不算故障**  
- 两边说法不一致时：**以 Temu 卖家后台页面为准**（赛狐有时同步慢）

### 3. 定时「我还活着」汇报

每天默认 **上午 9:30、下午 16:30**（可改）会推一次各店概况。  
即使没有异常也会发——用来确认插件还在跑，并列出 **当前限流清单 + 链接**，方便定点复盘。

## 四、从立项到现在，经历了什么？（给领导的故事线）

不讲技术细节，只讲「为什么要改、改完业务上好在哪」。

### 第 1 步（7 月上旬）：先做出来

- 需求：在售掉了要报、流量异常要报  
- 先在一台电脑上用自动浏览器试跑，打通飞书  

**遇到的现实问题：** 登录容易过期、Temu 防机器人、每人电脑环境不同 → **不适合发给每个运营当日常方案**。

### 第 2 步（7 月中）：改成 Chrome 小插件

- 装在 **大家自己日常用的浏览器**里，用已经登录好的账号  
- 支持 **一个人管多个店**：电脑空闲时才自动轮流切店看（避免打断正在操作）  
- 告警从「只报数字」升级到 **点名具体商品 + 可点链接**  

**业务价值：** 落地成本低，谁装谁用，各人飞书群自己配。

### 第 3 步（7 月底）：服务器上再加一条「上下架备份」

- 原因：插件依赖同事开着电脑；上下架希望 **下班、关机也有人盯**  
- 做法：公司服务器连「赛狐」接口，约每 15 分钟查一轮在售变化  
- 限流仍然只靠插件（赛狐没有这个数据）  

**业务价值：** 上下架有 7×24 底线；限流继续用更准的后台插件。

### 第 4 步（8 月）：插件再加强，专门治「乱报、漏报、刷屏」

运营侧实际遇到过、且已逐项处理的问题：

| 当时现象（业务语言） | 原因（通俗） | 现在怎么避免 |
|----------------------|--------------|--------------|
| 明明没下架，却报下架一大批 | 页面开着「限流筛选」，扫到的不是完整在售列表 | 扫描前先恢复干净列表再比 |
| 真的下架了 occasionally 没报 | 有的检查只在「电脑空闲轮巡」时做 | 恢复多种检查路径 |
| 一切换店铺，限流又推一遍 | 系统「忘了」刚才已经报过哪些商品 | 按商品 ID 记住 + 切换时静默消化 |
| 数字闪一下 15→4→15，连发两张卡 | 切店加载中的假数字 | 同一数字要稳定出现两次才认 |
| A 店的事报到 B 店头上 | 页面店名切换慢半拍 | 改用店铺唯一编号绑定 |
| 后台已下架，赛狐还显示在售 | 赛狐同步慢 | 插件以后台为准再报一层；赛狐继续做备份 |

**当前版本 v19.3** = 以上问题的集大成稳定版。  
不是「功能没做完所以版本号高」，而是 **监测类工具必须和真实后台「较劲」**，每发现一类误报就加一道确认，版本才会往上走。

## 五、请领导和运营建立的正确预期

### 我们保证优先做到的（红线）

1. **不串店**——A 店的事不报到 B 店  
2. **切换店铺不刷屏**——老限流不重复炸群  
3. **加载中的假数字不发告警**——避免 15→4→15 这种来回打卡  

这三条一旦出现，研发按紧急故障处理。

### 请理解可以接受的

| 情况 | 说明 |
|------|------|
| 同一商品两张上下架卡 | 双通道保险，看是否带「插件·后台」即可 |
| 赛狐比后台晚十几分钟甚至更久 | 正常；后台插件应更早 |
| 关机 / 关 Chrome / 没开商品列表页 | 插件实时能力暂停；上下架仍可能有服务器备份 |
| 告警晚几秒到几分钟 | 为了防误报，系统会「看稳了再报」 |
| 在售特别多、一页看不全时 | 可能先报「数量变了」，具体点名稍晚或靠下一轮 |

### 系统明确做不到的

- 替代官方所有运营动作（不能自动替你改价、申诉、重新上架）  
- 在完全没人开浏览器、且赛狐也异常时，保证限流 0 遗漏（限流只有插件能看）

## 六、运营同事日常怎么用（30 秒版）

1. Chrome 安装 / 升级插件到 **v19.3**（升级后请到扩展页 **关掉再打开** 一次，不要只点刷新）  
2. 点开插件，确认显示 **`后台：v19.3-mallId绑店`**  
3. 设置里填好自己的飞书群机器人地址，点「测试飞书」  
4. 打开并尽量保留：`商品列表` 页面（agentseller 后台）  
5. 正常上班即可；电脑空闲约 4 分钟以上可能自动轮巡其他店  
6. 收到飞书 → 点链接进后台处理；严重限流优先  

**反馈问题请尽量带齐：** 店名、时间、飞书卡片原文、插件弹窗截图（能看到版本号那行）。  
方便判断是「真问题」还是「双通道正常双报」。

## 七、当前结论与下一步（给领导拍板用）

### 结论

| 项 | 状态 |
|----|------|
| 核心目标（多店在售 + 限流自动飞书） | **已达成并在用** |
| 日常主方案 | **插件 v19.3** |
| 上下架 7×24 备份 | **服务器赛狐已上线** |
| 历史误报/刷屏类问题 | **已针对性收敛**；进入观察巩固期 |
| 旧的「每人电脑跑自动浏览器」 | **已停止作为日常方案** |

### 建议的管理动作

1. **统一版本**：相关运营全部升到 v19.3，旧压缩包停用  
2. **观察 48 小时**：非「串店 / 刷屏 / 数字来回打」类问题，先记录不频繁改版  
3. **接受双报策略**：上下架双通道保留，稳定优先于「群绝对安静」  
4. **研发侧暂缓新功能**：先巩固准确率与文档/发版纪律，避免再靠「出一张卡修一版」  

### 需要领导知情的取舍

- **更准** 往往意味着 **稍慢一点报**（要确认不是页面闪一下）  
- **更稳** 往往意味着 **两条通道都报**（偶尔多一张卡）  
- 若要求「群里绝对不能双卡」或「关掉 Chrome 也要限流 0 遗漏」，需要另开需求、单独评估成本

## 附：三句话收尾（口播可用）

1. **这个项目解决的是**：多店掉链接、被限流，人刷不过来，要自动推飞书。  
2. **现在的用法是**：同事装插件盯限流和实时上下架；公司服务器用赛狐做上下架备份；两边都推、以后台为准。  
3. **版本比较多是因为**：后台在**切店、加载、筛选**时，页面上会出现**一闪而过的中间态数字**（例如在售 15 瞬间显示成 4 又恢复），不是业务真变了。系统要先「看稳了再报」，才能少误报、少刷屏；当前 v19.3 是稳定基线，接下来重点是全员统一版本和巩固观察，而不是继续堆新功能。
