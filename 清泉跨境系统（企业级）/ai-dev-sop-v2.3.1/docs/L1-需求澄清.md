# L1 — 需求澄清

> 目标：模糊一句话 → **可开发 Spec**。未过 DoR 禁止编码。

## 1. 为什么 L1 是一等公民

需求经常不完整。若跳过 L1，Agent 会用「合理猜测」填洞，直到交付才爆。

```text
甲方填 INTENT-raw（白话收集）
  → 产品整理成 INTENT（templates/INTENT.md，至少 §0）
  → /ai-dev-sop + 粘贴 INTENT
  → 八维缺口扫描
  → 3–5 问/轮（安全优先）
  → 假设 [ASSUMES:]
  → 填 SPEC + ACCEPTANCE
  → DoR / check-dor.sh
  → SPEC READY → 批准
  → PHASE 2 MVP → PHASE 3 架构 → Plan / 开发
  → 每步交付物进仓（见 节点交付物.md）
```

| 模板 | 谁填 |
|------|------|
| [`INTENT-raw.md`](../templates/INTENT-raw.md) | 甲方 / 业务（收原始需求） |
| [`INTENT.md`](../templates/INTENT.md) | AI 产品经理（整理后喂 SOP） |

示例：[`INTENT-raw-example`](./specs/INTENT-raw-example.md) · [`INTENT-example`](./specs/INTENT-example.md)

Agent 细项：`skill-pack/01-req-clarify/` + `references/l1-scan-dimensions.md`

## 2. 八维（背标题即可）

1. 用户与场景  
2. 目标与成功标准（可观测）  
3. 范围：In / **Out≥3** / Non-goals  
4. 主流程 + 异常（**Edge≥3**）  
5. 数据与权限 / 敏感数据  
6. 集成依赖  
7. 非功能  
8. **合规与发布边界**（或整维 N/A + 理由）

展开项：[`templates/spec-compliance-checklist.md`](../templates/spec-compliance-checklist.md)

## 4. DoR 检查表

- [ ] 确认「可以按此 Spec 开发」
- [ ] 每条主功能 ≥1 happy + ≥1 error
- [ ] Out of Scope ≥ 3
- [ ] 未关闭 Open Questions ≤ 2
- [ ] Edge ≥ 3
- [ ] 无不可测措辞
- [ ] 维 8 已填或 N/A
- [ ] （推荐）脚本通过：

```bash
./skills/ai-dev-sop/scripts/check-dor.sh docs/specs/SPEC-xxx.md docs/specs/ACCEPTANCE-xxx.md
```

## 5. 人怎么配合 Agent

| Agent 行为 | 你做什么 |
|------------|----------|
| 一次问 1–5 个问题 | 简短如实答；不知道就说不知道 |
| 写出 `[ASSUMES: …]` | 接受 / 否定 / 改成明确需求 |
| `SPEC READY` | 通读后回复**批准**或列修改点 |
| `MVP READY`（Spec 批后） | 确认本迭代 Ship-now / Defer / Success；回复**批准** |
| `ARCH READY`（MVP 批后） | 看模块图/边界是否支撑 Ship-now；或批 N/A |
| 想扩 scope | 你决定：写入 Out of Scope、Defer，或降优先级 |

**Out of Scope 必须人主导**——Agent 倾向把范围做大。  
**MVP 切片必须人主导**——Spec 全量 ≠ 本迭代全做。

---

## 6. 打回规则

开发中若目标/范围/验收变更 → **回到 L1**，改 Spec 并重新批准。  
仅本迭代交付面变化 → **回到 PHASE 2** 改 MVP 并再批。
