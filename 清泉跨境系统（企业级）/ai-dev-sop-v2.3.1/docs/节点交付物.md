# 节点交付物（员工开发场景）

> **原则**：每个硬门禁 = **哨兵句 + 人批准 + 进仓制品**。  
> 对话里的同意不算完成；制品路径写入工作区（建议 `docs/specs/`）。  
> Agent 总控见 `skills/ai-dev-sop/`；本表给人与管理者对齐「交什么、谁批」。

## 1. 总表

| PHASE | 节点 | 哨兵句 | 进仓交付物（必须） | 默认审批人 | 可 skip / N/A |
|-------|------|--------|-------------------|------------|---------------|
| 0 | 识别 mode | —（状态报告） | 对话/状态中写明 `feature` \| `greenfield` | 执行者自认；存疑问上级 | — |
| 1 | L1 Spec | `SPEC READY` | `SPEC-<slug>.md` + `ACCEPTANCE-<slug>.md`；（可选）合规表 | **产品/负责人** | 否 |
| 2 | MVP | `MVP READY` | SPEC §2.4 或 `MVP-<slug>.md`；ACCEPTANCE「MVP Demo」对齐 | **产品/负责人** | 热修可 skip（记理由） |
| 3 | 架构 | `ARCH READY` | `ARCHITECTURE-<slug>.md`（模块图 + 边界 + 关键决策） | **技术负责人**（可与产品会同批） | 见 §2；须写 N/A 或 skip 理由 |
| 4 | Plan | `PLAN READY` | `PLAN-<slug>.md`（或 PR/对话落盘等价物，路径须固定） | **技术负责人** 或执行者上级 | 热修可 skip |
| 5 | Findings | `FINDINGS READY` | Findings 节（可附在 PLAN 或独立短文） | 执行者上级 / 技术负责人 | greenfield 可 N/A；热修可 skip |
| 6 | 实现 | — | 代码 + 测试/手工验证记录（对照 MVP Demo） | （过程检视，非硬哨兵） | — |
| 7 | Diff / PR | `DIFF READY` | Diff Summary + PR 描述（链 SPEC/MVP/ARCH/PLAN） | **技术负责人** 或指定 reviewer | **不可跳** |
| 8 | 回写 | — | （可选）3–5 条规则进 `AGENTS.md` | 执行者 | 可选 |

## 2. 架构（Gate D）何时必须 / 可 N/A

| 情形 | 要求 |
|------|------|
| greenfield、新服务、新模块边界 | **必须**完整 ARCH（含 mermaid） |
| 跨模块 / 改数据模型 / 新外部集成 | **必须**（可画增量图：现有 + 变更） |
| 单文件、无边界变化的小改 | 可 **N/A**：`ARCHITECTURE-*.md` 写明理由，仍输出 `ARCH READY` 等人批 |
| 用户书面热修、拒绝完整 SOP | 可 **skip** Gate D（与 M/A/B 同）；**不可** skip Gate C |

## 3. 三层「看见什么」

| 制品 | 看见 |
|------|------|
| MVP | 本迭代**交付面**（用户能感知什么） |
| ARCHITECTURE | 系统**内部结构**（模块、数据流、边界） |
| PLAN | **怎么落地本迭代**（改哪些文件、验证步骤） |

三者都批后才允许写业务代码（热修 skip 除外）。

## 4. 管理者检查口诀

1. 有没有路径？只活在聊天里 → 打回  
2. MVP 是否 ⊆ Spec？架构是否支撑 Ship-now？Plan 是否 ⊆ MVP？  
3. Diff 是否超出 Plan/ARCH？  
4. 任一 skip/N/A 是否写了理由？
