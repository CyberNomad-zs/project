## §1 问题与工作

### 1.1 问题陈述

- **现状（As-Is）**：
  - Temu：插件/Playwright 巡店异常 → 飞书告警
  - TikTok：紫鸟插件抓广告 → 飞书多维表 + 日报
  - 海外仓：赛狐 API 桥 → 发货闭环 + 飞书对账告警
  - 无统一自建平台；飞书被当成「主界面」
- **摩擦点**：多系统切换；管理层看不到「员工如何处理异常」；数据资产与行为未闭环进库，无法沉淀知识库
- **理想结果（To-Be）**：
  - **自建平台 = 主体**（数据中枢 + 全量展示 + 行为留痕）
  - 飞书 = **展示/通知适配层**（可选镜像，非系统中心）
  - 采集层（API/脚本/插件/RPA）持续灌入运营与行为数据 → 知识库 → 逐步全自动化

## §2 范围直觉

### 2.1 第一期希望有（In · 调研建议）

1. 统一 **Case**（Temu 告警 / TK 风险行 / 仓 FAILED·无渠道·对账差异 → 建案）— **[ASSUMES: 1.0 先这三线]**
2. 员工工作台：认领 / 填处置 / 关闭（无此则无法做 B）
3. 管理层监督台：按人、按店、SLA/超时
4. 案件时间线复盘（A+B）
5. 过程事件模型 + 自创字段（处置码、理由、误报、结果标签）
6. 飞书仅通知+深链；C 能力架构预留不实现

详见 `RESEARCH-qingquan-work-data.md` §3–§6。

### 2.2 第一期不要做（Out）

1. 再造完整跨境 ERP / 广告 BI
2. **C：建议引擎 / 自动规则执行 / 全自动替代员工**
3. 键鼠/桌面级员工监控
4. （参考）补货改造；Amazon/采购线可二期

### 2.3 方案直觉（未批准设计）

- **架构纠正（相对原流程图）**：

- 业务：各平台「员工日常工作」字段定义不清；亚马逊线在既有三项目中**几乎空白**（海外仓实为 Temu 履约）

## §3 流程与异常（草稿）

### 3.1 主路径（巡店异常闭环 — 流程图最清晰的一条）

1. 采集写入自建库（店铺/商品/广告/订单等运作数据）
2. 规则引擎判定异常
3. 通知负责人（平台内 +/或 飞书）
4. 负责人在平台（或约定渠道）处理并提交反馈
5. 处理方式与效果回写数据库留痕  
**完成标志**：异常单状态闭环且库中可审计

### 3.2 失败/边界期望

| 情况 | 期望行为 |
|------|----------|
| 采集失败 / 登录过期 | 告警；平台标红；不静默丢数据 |
| 无人认领异常 | 未知（升级？超时？） |
| 飞书不可用 | **平台仍可用**（飞书非主体） |
