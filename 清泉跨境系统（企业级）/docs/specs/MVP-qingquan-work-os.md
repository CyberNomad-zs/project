## 0. 先用一分钟看懂 MVP 是什么

**MVP = 这一刀做完后，你们公司立刻能用起来、能演示给老板看的最小产品。**

> 店里出了问题 → 系统里出现「待办案件」→ **飞书群里喊一声并 @该处理的人** →  
> 员工点进平台认领、写清怎么处理、关闭 →  
> 老板在监督台看谁超时、谁没动 →  
> 点开任意一条能看到全程记录。

**主体仍是自建平台**（案件、监督、留痕都在平台）。  
**飞书是通知渠道（必做）**，不是主数据库、不是主界面。

**这一刀刻意不做：**  
跨境 ERP、广告大屏、飞书当主库、**智能推荐**、自动改广告/发货、监控键鼠、按级别选「群或个人」的复杂路由（下版做）。

## 2. 这一刀要交付的 6 件事（Ship-now）

### ① 案件本子
未认领 → 处理中 → 已关闭；关闭必填处理方式 + 原因说明（自创数据，给以后推荐攒原料）。

### ② 出事能进系统
Temu 优先真告警（或演示）；TK/履约可用演示数据证明同模型。

### ③ 员工工作台
认领 → 填处置 → 关闭；没认领/没原因关不掉。

### ④ 老板监督台
未闭环数、超时数、按人/店筛选、超时红灯。

### ⑤ 案件时间线
谁、何时、做了什么，完整可查。

### ⑥ 飞书群通知（**必做 · 本次新增升格**）

| 白话 | 说明 |
|------|------|
| 走到哪 | **飞书群**（不是先做个人私聊） |
| 什么时候推 | 至少：**新建案件**、**超时未处理**；关闭成功可推一条「已关闭」（可选） |
| @谁 | 把「该处理的人」拉进/配置进对应群；消息里 @这些人（或飞书等价提醒） |
| 消息里有什么 | 简要事由 + 店铺 + **点进平台的链接** |
| 怎样算做成 | 配置好群机器人后，建一条演示案，群里能看到通知；飞书挂了时平台仍能建案处理，但系统记下「通知失败」 |
| 下版再做 | **按通知级别**：普通走群 / 紧急走个人（或群+个人）——本期不做级别路由，规则先写进配置预留字段亦可 |

## 3. 超时默认（可改）

| 类型 | 认领时限 | 关闭时限 |
|------|----------|----------|
| Temu 告警 | 4 小时 | 24 小时 |
| TK 风险 | 8 小时 | 48 小时 |
| 履约例外 | 2 小时 | 12 小时 |

超时：监督台红灯 **且** 尝试再发飞书群提醒。

## 4. 智能推荐（C）— 你的决定已写死

| 现在 | 以后 |
|------|------|
| **不做**推荐界面、不做自动处置 | 用 ①⑤ 攒够的过程数据再做 |
| 字段照样存：处理方式、原因、结果、是否误报 | 那是推荐的原料 |

---

## 5. 演示验收（Success check）

1. 案件：认领 → 填原因 → 关闭 → 时间线完整  
2. 监督台：能看到超时与责任人  
3. **飞书群：能收到新建（或超时）通知，含可点开的平台链接**  
4. 页面上没有「智能建议」  
5. 故意关掉飞书配置时：平台闭环仍可做完，并有通知失败记录  

---

## 6. 这一刀明确不做

1. 按级别自动选「群通知 vs 个人通知」（下版）  
2. 智能推荐 / 自动改广告发货  
3. TK/仓生产级全量接入（演示即可）  
4. 亚马逊 / 采购线  
5. 飞书当主数据库、飞书登录 SSO  
6. 键鼠监控
