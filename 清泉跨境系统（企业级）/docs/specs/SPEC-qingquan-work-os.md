## 1. BRIEF — 问题与目标

### 1.1 原始需求（用户原话）

- INTENT：`docs/specs/INTENT-qingquan-platform.md`
- RESEARCH：`docs/specs/RESEARCH-qingquan-work-data.md`
- INTENT-raw：`docs/specs/INTENT-raw-qingquan-platform.md`

```text
【§0 摘要】
补齐市面跨境系统缺的三块：员工监督、对人做事的记录与学习、公司自创/过程数据。
市面只做跨境经营+平台官方数据；我们要监督人、留痕、沉淀可学习资产。
1.0 = A（存查）+ B（按人/按事复盘）；C（建议/自动）仅架构预留。
认可默认假设：1.0 接 Temu+TK+仓；执行者必须在平台认领/关闭；不做桌面监控/C引擎/完整ERP。
```

### 1.2 问题陈述

- **谁：** 传统跨境外贸公司的老板/管理层；运营、广告运营、履约跟单等执行角色。
- **问题：** 现有能力（Temu 告警、TK 日报、仓发货桥）能发现事，但看不到「谁在做、是否按时、怎么处理、结果如何」；过程与自创数据未入库，无法形成组织记忆。
- **不做的后果：** 继续依赖飞书喊人与个人经验；无法监督；无法为后续知识库/自动化（C）积累原料；变革停在「又多几个脚本」。

### 1.3 目标用户与场景

| 角色 | 场景 | 频率 |
|------|------|------|
| 老板 / 管理层 | 打开监督台：按人/按店看待办、超时、未闭环；点开案件看时间线 | 每日 |
| 店铺运营（Temu） | 在工作台认领下架/限流类案件，填写处置并关闭 | 每日多次 |
| 广告运营（TikTok） | 认领低 ROI / 零产出花费风险案，记录决策并关闭 | 每日 |
| 履约跟单（海外仓） | 认领无渠道/FAILED/对账差异案，记录处理并关闭 | 每日多次 |
| 系统管理员 | 维护用户角色、默认 SLA、飞书 Webhook（若启用） | 按需 |

### 1.4 成功标准（可观测）

- [ ] 来自 Temu 告警 / TK 风险行 / 仓 FAILED·无渠道·对账差异 的信号能建成 Case，并在平台列表可见
- [ ] 执行者完成「认领 → 填写处置（含 disposition + rationale）→ 关闭」后，案件时间线含 actor、activity、ts、outcome
- [ ] 管理层监督台能按人、按店筛选，并对超过 SLA 且未关闭的案件显示超时标识
- [ ] 至少一类自创数据可查询：处置码、误报标记、或关闭结果标签（非平台原始字段）
- [ ] 飞书不可用时，平台上述能力仍可用（飞书仅为通知适配）
- [ ] 数据模型含 C 预留字段（disposition_code / rationale / outcome_label），1.0 **无**「系统建议处置」功能

### 1.5 非目标（Non-goals）

- 再造跨境 ERP / 多平台广告 BI / 拼平台官方数据完备度
- 1.0 实现建议引擎、自动规则执行、自动替代员工处置（C）
- 键鼠/桌面级员工监控
- Amazon 巡店、采购线、补货流程改造
- 修改海外仓自动下单/回传业务逻辑本身（仅把需人工介入的状态变成 Case）

## 3. 主流程

### 3.1 Happy path

1. 接入层收到 Temu 告警 / TK 风险 / 仓人工例外信号 → 创建 Case（`open`）并写创建 事件  
2. 飞书群收到新案件通知（@需处理人 + 平台深链）；站内待办池同时可见  
3. 运营在工作台 **认领** → 状态 `claimed`，事件记录 actor  
4. 运营填写 `disposition_code` + `rationale`（必填）及 `outcome_label` / `false_positive`（按类型）→ 可多次备注  
5. 运营 **关闭** → 状态 `closed`，写 close 事件；时间线完整可查  
6. 管理层在监督台按人/店查看；未超时且已关闭的案不再显示超时红灯  

**Case 状态机（1.0）：** `open` → `claimed` → `closed`；支持 `open|claimed` → `reassigned`（改派后仍为 claimed 属新 actor）。不允许跳过认领直接关闭。

**默认 SLA（可配置，见假设 A5）：**  
- `temu_alert`：首次认领 4 小时，关闭 24 小时  
- `tiktok_risk`：首次认领 8 小时，关闭 48 小时  
- `fulfillment_exception`：首次认领 2 小时，关闭 12 小时  

超时定义：超过「首次认领 SLA」仍为 `open`，或超过「关闭 SLA」仍未 `closed` → 监督台标记超时。

### 3.2 异常与边界（≥ 3；详情见 ACCEPTANCE）

1. 飞书 Webhook 失败：Case 仍创建；记录通知失败；平台可用  
2. 重复信号（同一业务键短时间重复）：不新建重复 open Case，追加事件或忽略（幂等键见假设 A6）  
3. 无权限用户访问他人案件或监督台：拒绝并提示  
4. 关闭时缺少 disposition_code 或 rationale：拒绝关闭并提示  
5. 采集源长时间无信号：不影响已有 Case；管理端可看到「接入心跳」状态（P1，不阻断 1.0 闭环演示）

## 4. 数据与权限

| 实体/数据 | 读 | 写 | 角色 | 敏感？ |
|-----------|----|----|------|--------|
| Case | 经理全量；运营：未认领池+本人案件 | 系统建案；运营认领/关闭；经理可改派 | manager/operator/admin | 中（含经营异常上下文） |
| CaseEvent（过程） | 同 Case | 仅系统/操作产生 append | 同上 | 中（含员工行为） |
| User / Role | admin 全量；自己可读 | admin | admin | 低 |
| 店铺/上下文快照 | 随 Case | 接入层 | 系统 | 中（店铺名、指标） |
| 凭据（平台登录/API Key） | **不进本系统业务库** | N/A | — | 高 → 禁止入库 |

权限模型（一句话）：**经理看全局监督与复盘；运营只处理待办与本人案件；管理员管账号与 SLA/通知配置；无人可在 1.0 触发自动写回电商平台。**

数据删除/保留策略：Case/Event **默认不物理删除**（软删仅 admin）；保留期限默认 24 个月或直至公司另定（假设 A7）。员工过程数据用于业务复盘，**不**用于隐蔽监控产品叙事。
